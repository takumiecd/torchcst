# FlashAttention型の厳密CSTタイル融合をL4で反証（2026-09-29）

## 狙いと対象

FlashAttentionの「中間行列を小タイルとしてon-chipで作り、その場で使用する」構成をCSTへ適用した。ここで学習するのは**CSTのatomパラメータ**であり、低ランク因子へのモデル変更はしない。論理Wも局所dWも、融合kernelはグローバルな重み窓へ書き出さない。

Colab ProのNVIDIA L4、PyTorch 2.11.0+cu128、Triton 3.6.0、1024×1024、64×64 station、5%（52,429 atoms）、seed 21、入力行数16/128。比較は同じatomと入力で行った。CUDA Graph再実行を32巡交互に測った前向きと、CUDA eventを24巡交互に測った512出力行ぶんの局所逆向きである。どちらも候補リストと現在のatomの配置準備は測定範囲外。**完全AdamWステップの速度は測っていない。**

## 実装

前向き融合kernelは、既存の安全な候補atomリストから16×64のWタイルをレジスタ上に生成し、`tl.dot(X_tile, W_tile.T)`で部分出力を作る。入力列方向を複数programに分け、部分出力を二番目のkernelで足す。Wの計算は現行Triweightと同じで、atom値を毎回読む。候補192枠のあふれは0件。出力は独立のcanonical Wからの行列積に対して、M=16/128の全候補で `atol=rtol=3e-5` 違反0。

| 入力行数 | 既存W生成＋GEMM（Wタイル8×64） | 融合forward最良 | 融合/既存 |
| ---: | ---: | ---: | ---: |
| 16 | 0.252 ms | 0.278 ms（BM16、入力列64ずつ） | 1.10 |
| 128 | 0.319 ms | 0.495 ms（BM128、入力列64ずつ） | 1.55 |

同じ16×64のWタイル生成と比べるとM=16で0.292→0.278 msと小幅に速いが、現行最速の8×64経路には負ける。M=128をBM16で処理すると、同じWタイルを8回作るため2.23 msまで遅くなる。BM128でWを再利用しても0.495 ms。入力列を2タイルまとめる構成は243 registers/thread、4タイルでは366 spills/threadで、速度も悪化した。部分出力scratchはM=16・1タイル分割で1 MiB、M=128では8 MiB。

局所逆向きは既存の候補リスト付き`mapped_backward_atoms_listed(..., FUSED_DW=True)`を用いた。`dW_tile=dY_tile.T @ X_tile`をkernel内で計算し、その場でCSTのatom勾配に縮約する。比較経路は同じ512出力行について`torch.mm`で局所dW窓を作り、別kernelでatom勾配に縮約する。両者のatom勾配は `atol=rtol=3e-4` 違反0。結果は以下。

| 入力行数 | 局所dW＋atom勾配 | 融合dW＋atom勾配 | 融合/既存 | atom勾配相対L2差 |
| ---: | ---: | ---: | ---: | ---: |
| 16 | 0.337 ms | 0.559 ms | 1.66 | 2.02×10⁻⁷ |
| 128 | 0.325 ms | 0.610 ms | 1.88 | 3.15×10⁻⁷ |

## 判断

今回の**厳密なFlash型融合は採用しない**。現行最速経路に比べ、前向きとatom勾配側の局所逆向きがともに遅い。入力勾配の融合版は未実装で、したがって完全ステップの速度改善を主張できない。測定済みの二段階が既に不利なため、その実装に進む優先度は低い。

1024²のFP32 Wは4 MiBで、L4の48 MiB L2に収まる。既存経路は一度生成したWを行列積と入力勾配に再利用できる。Flash型融合ではグローバル書き込みを減らしても、候補atomの値とTriweightを別CTAや逆向きで再計算する。今回のデータは、**site×atom評価とatom勾配の費用が、W/dW窓の読み書き削減より大きい**ことを示唆する。これは原因の推定であり、L2トラフィックと演算器使用率の詳細profileまでは測っていない。

次にCSTを速くするなら、単なるon-chip融合より、**真のTriweightを評価するsite×atomの組を減らすこと**を先に検証する。候補は[固定アンカー補間](cst-1024-algorithm-redesign-20260929.ja.md)だが、atom勾配と更新後誤差、完全ステップは未検証である。RTX 6000 Adaは別ジョブがGPUを使用していたため今回の測定には使っていない。
