# 5% atom密度：局所重みを先に作って入力へ使い切る

2026-09-28。`atom数 = round(0.05 × N × K)`、A100 80GB PCIe MIG 3g.40gb（42 SM）、FP32、TF32無効、seed21。全論理重み `W[N,K]` を保持せず、局所重み窓を作って入力の全行に使い、同じbufferを次の窓へ使い回す。

```text
for output-row window R:
    W_R = generate_from_current_CST_atoms(R, all_input_columns)
    Y[:, R] = X @ W_R.T
    reuse W_R storage for the next R
```

これは既存 `triton_streamed` のループ順である。以前の16入力測定はこのforwardを16回呼び、毎回窓を再生成していた。今回の測定は同じ16組の入力を2048行の1つのバッチとして渡し、各窓を1回だけ生成した。別々の入力を扱う実装でも、窓を外側、入力群を内側に回せば同じ再利用を狙える。ただし入力群の処理中はatom値を更新しない。学習時の複数microbatchではactivation保持と更新タイミングを別途設計する必要がある。

局所窓は出力行1024なら4096²で16 MiB、8192²で32 MiB。256行なら4／8 MiB。`torch.mm` は局所窓のGEMMに使うが、全Wを作る経路ではない。

## バッチを大きくした測定

各モードを独立プロセスで測り、全出力を同じCSTから作ったdense oracleと `atol=rtol=3e-5` で照合した。各runのcanonical W 1,152点も合格。表はwitness付きstreamedの1024行窓と、生成済みdense比較。時間はCUDA Graph、ピークは通常forwardで `max_memory_allocated`。dense Wの生成時間はdense側に含まない。固定幾何とhintはstreamed側の常駐量に含めた。

| 重み形状 | 入力行 M | dense 時間 | 局所窓 時間 | dense ピーク | 局所窓 ピーク |
| --- | ---: | ---: | ---: | ---: | ---: |
| 4096² | 128 | 0.663 ms | 11.738 ms | 76.12 MiB | 86.73 MiB |
| 4096² | 512 | 2.635 ms | 13.615 ms | 88.12 MiB | 95.00 MiB |
| 4096² | 1024 | 5.066 ms | 17.289 ms | 104.12 MiB | 103.13 MiB |
| 4096² | 2048 | 9.582 ms | 21.924 ms | 136.12 MiB | 130.39 MiB |
| 8192² | 128 | 3.023 ms | 47.088 ms | 272.12 MiB | 317.29 MiB |
| 8192² | 512 | 10.234 ms | 54.856 ms | 296.12 MiB | 329.29 MiB |
| 8192² | 1024 | 19.880 ms | 69.905 ms | 328.12 MiB | 345.29 MiB |
| 8192² | 2048 | 37.197 ms | 84.925 ms | 392.12 MiB | 377.29 MiB |

2048行の4096²では、局所窓の全Wなし経路がdenseより5.73 MiB少なく、約2.29倍の時間。8192²では14.83 MiB少なく、約2.28倍の時間。**メモリ条件を満たすのはこの測定では大きい入力バッチに限られ、削減幅も小さい。** 以前の16回独立streamed呼び出しは187.540／747.421 msだったので、CST側の窓を先に作る順序には大きな効果がある。ただし2048行バッチ自体の入力・出力保持量は128行の場合より大きい。同じ合計入力を処理する比較として解釈する。

## 局所窓をさらに小さくする

M=2048、witness付き経路を同条件で測った。4096²では256行窓が1024行窓とほぼ同速でピークを11.39 MiB下げた。8192²では窓を小さくしてもピークは変わらず、配置準備中の割当が支配している。

| 重み形状 | 窓の出力行 | 窓の容量 | 時間 | 合計ピーク |
| --- | ---: | ---: | ---: | ---: |
| 4096² | 1024 | 16 MiB | 21.924 ms | 130.39 MiB |
| 4096² | 512 | 8 MiB | 22.277 ms | 122.39 MiB |
| 4096² | 256 | 4 MiB | 22.017 ms | 119.00 MiB |
| 8192² | 1024 | 32 MiB | 84.925 ms | 377.29 MiB |
| 8192² | 512 | 16 MiB | 83.337 ms | 377.29 MiB |
| 8192² | 256 | 8 MiB | 86.684 ms | 377.29 MiB |

次の改善対象は、局所窓の生成とGEMMを重ねる実行順序、および配置準備のsort・decode・packに伴う大きな一時領域である。窓だけをさらに小さくしても8192²のメモリピークは下がらない。小バッチでもdense未満のピークを満たし、速度を詰めるには準備処理のscratch削減が必要。
