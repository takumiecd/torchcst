# 単独タイル・境界共有アトムの配置

## 設計条件

CSTの小さなパラメーター表現とcompact kernelの局所性を保ち、
GEMMの入力再利用・局所タイル内の積和を利用する。
実行経路で全重み `W[N,K]`、全重み勾配 `dW[N,K]` をHBMへ展開しない。
Chartのtileと、GPUの内部計算タイル `BM,BN,BK` は別の単位。

旧実装は最近傍の所属タイルでまとめ、左右を含む3所属の全アトムを読んだ。
今回、実際に支持するタイルで区分する。配置は次の通り。

```text
I[0], B[0], I[1], B[1], ..., I[G-1], B[G-1], idle

I[g] : タイルgのみに非ゼロの寄与を持つ
B[g] : タイルgと(g+1)%Gの両方に寄与する
idle : 現時点ではどの観測サイトにも寄与しない

タイルgが読む区間 = B[g-1], I[g], B[g]
```

アトム本体を重複させない。G=2では両方に寄与するアトムをB[0]へまとめ、
G=1ではI[0]だけを使う。idleも削除せず、固定個数のパラメーター表に残す。
更新で支持先が変われば次回forwardの分類へ反映する。
標準パラメーター表 `p` の順序は保持し、実行用の表をstable sortで作る。
backwardで勾配を元の順序へ戻すため、optimizerの状態を並べ替える必要はない。

## 支持先の判定

既存のChart検証で最大2つの隣接タイルという条件を確認する。
最近傍の所属とその左右を調べ、実際のサイトへの距離について
`distance_squared * precision < 1` を満たす点があるかを判定する。

Strip＋Torusでは入力列ごとの半径が正であり、最近傍の行方向は列に依存しない。
そのため、候補タイル内の最近傍行を選び、その行の列だけを調べればよい。
判定時に `[atoms,N,K]` は作らない。CPU参照版はアトムと列をchunk化し、
GPU版はアトムごとに列を走査する。支持先の離散判定は微分せず、
パラメーターの評価式・帯域幅のstop-gradientは既存のものを使う。

支持境界付近のFP32判定は数値精度に依存する。CPUの全サイトによる支持oracle、
GPU分類との照合、既存の4種類のprofileの出力・一次勾配を検証する。
全アトムがidleの場合も入力・パラメーターへのゼロ勾配を維持する。

## 実行と再利用

PyTorch tiledとTritonのforward、dX、dPが同じ区分を使う。
Triton内では従来同様、小さな重みタイルを生成して直後の積和に使い、
dPでは小さなdWタイルからアトムの勾配を集計する。全W/dWは生成しない。
境界共有アトムのdPは両タイルから加算される。

メモリ配置の改善は、不要な所属区間を読み込まなくなることと、
同じ依存先のアトムが連続すること。キャッシュhit率そのものは未測定。

内部の `batch_tile` を16/32/64で比較する。同じ局所重みをより多くの
入力行で共有できる一方、出力累積値のレジスタ使用量が増え、
GPU上の同時実行数が下がる可能性がある。大きければ速いとは決めない。
実験用引数であり、公開APIへハードウェア向けの調整値を増やさない。

現段階ではタイル内の全K区間を走査する。列方向の支持範囲による仕事の削減、
永続的に保持したアトム配列の差分repack、明示的な共有メモリへの先読みは未実装。
境界分類の準備コストも含め、保持済みdenseと既存CSTを比較する。

pytest -q tests/test_support_layout.py tests/test_triton_linear.py
python -m prototypes.benchmark_support_layout --output support-layout.json --source-commit COMMIT
