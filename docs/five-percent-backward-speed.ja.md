# 5% mapped CST：backwardの計算順序と速度

2026-09-28。前段の[学習メモリ測定](five-percent-mapped-training-memory.ja.md)と同じ5% atom密度、FP32、TF32無効、A100 80GB PCIe MIG 3g.40gb（42 SM）、64×64 CST tileを使った。Mは線形層へ入る総行数。単層のAdamWステップでforward、入力勾配、atom勾配、更新を含む。全重みWと全重み勾配dWはCST経路で保持しない。

## 時間を使う場所

4096²・M=128の旧backwardを個別に計時すると、入力勾配は9.74 ms、atom勾配は49.64 msだった。旧atom勾配は16×16の論理サイトタイルで局所dWを計算し、そのタイルの候補atomを評価してglobal gradientへatomic加算する。forwardで使っていた列方向の幾何情報共有は、この経路では使っていなかった。

二つの試作を追加した。

1. `factored`：forwardの列方向距離計算の共有をatom勾配へ移し、サイト座標をatomループの外で読み、atomとサイトの差を振幅・中心勾配に使い回す。16×32のdWタイル、atomレーン8を使う。
2. `staged`：入力勾配の局所重み窓が終わったら、**同じ最大1024×Kのバッファ**を局所dW窓に転用する。各行窓のdWを `torch.mm(dY_window.T, X, out=window)` で計算し、factored kernelでatom勾配へ縮約してから上書きする。4096²では窓16 MiB、8192²では32 MiB。全dWを保持しない。

`staged` の行窓はforwardから保存したpacked atom配置と固定サイト幾何を再利用する。重み窓自体をforwardから保持するとactivationと共存してピークを上げるため、現試作ではbackwardの入力勾配時に再生成する。

## 学習ステップの結果

単位は10進MBと同期wall ms。旧・factored・stagedは同じatom数、初期値、入力を使う独立プロセス。denseは従来の対照。時間はウォームアップ後のステップ。ピークはoptimizer状態初期化後の `torch.cuda.max_memory_allocated()`。各経路で初期重みのcanonical点と全出力を照合した。

| W形状 | M | dense | 旧CST | factored | 旧staged | staged FMA | listed 1 warp | listedピーク / denseピーク |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 4096² | 128 | 3.94 ms | 73.95 ms | 63.37 ms | 63.29 ms | 58.58 ms | **39.22 ms** | 174.96 / 358.88 MB |
| 4096² | 2048 | 30.29 ms | 119.93 ms | 100.50 ms | 90.46 ms | 86.47 ms | **66.92 ms** | 302.18 / 453.25 MB |
| 8192² | 128 | 14.93 ms | 290.83 ms | 249.08 ms | 247.93 ms | 230.21 ms | **148.09 ms** | 589.32 / 1371.80 MB |
| 8192² | 2048 | 119.06 ms | 475.44 ms | 未計測 | 354.04 ms | 339.32 ms | **256.98 ms** | 840.56 / 1560.54 MB |

2048行の旧CSTと旧stagedは同一ソース `98ce184` で各3回計測した中央値。4096²は旧119.93/119.91/120.12 ms、旧staged90.69/90.46/90.40 ms。8192²は旧479.22/475.44/458.77 ms、旧staged356.16/354.04/337.48 ms。旧128行は各1回の確認値。`staged FMA` は `23bf5a9` で4096²を各3回、8192²を各2回計測した中央値で、旧stagedから4096²・M=128で7.4%、M=2048で4.4%、8192²・M=128で7.1%、M=2048で4.2%短縮した。FMA融合だけの局所atom勾配は9.65→8.60 ms/1024行窓、勾配差の最大絶対値は1.83×10⁻⁴。旧経路のピークは計測した各経路で同じだった。4096²・M=512の旧予備測定ではfactored70.91 ms、旧staged68.66 ms、ピークはいずれも198.93 MB。`listed 1 warp` は `aef67b6` で各3回計測した中央値で、`staged FMA` より順に33.0%、22.6%、35.7%、24.3%短い。8192²の3標本には8%程度のばらつきがある。

小形状128²・192²の入力勾配とatom勾配を独立したPyTorch参照と照合し、atomを支持域境界・idleへ動かした128²も含めて24テストがA100で通った。大形状の全atom勾配を独立参照と照合したわけではないが、測定ステップではパラメータ勾配と入力勾配が有限かつ非ゼロであることを確認した。4条件すべてで初期重みのcanonical点と全出力も照合済み。atomic加算の順序は非決定的。準備処理の `torch.sort` 一時差し替えも試作のまま。

## 追加で試したbackward経路

`staged` でも4096²・M=128はdenseの約16倍、M=2048は約3倍かかる。そこで、同じ5%初期配置とA100で次を検証した。すべて全重みW・全dWを保持しない試作で、既定のbackendは変更していない。

| 4096²の方法 | M=128 | M=2048 | 1024行dW窓のatom勾配 |
| --- | ---: | ---: | ---: |
| 旧`staged` | 63.29 ms | 90.46 ms | 約9.6 ms |
| 現行`staged`（FMA融合） | **58.58 ms** | **86.47 ms** | **8.60 ms** |
| stationごとにatom勾配をまとめる `atom_major` | 69.78 ms | 97.69 ms | 最良のタイル調整でも10.23 ms |
| atom勾配と重み窓の再生成を融合する `fused` | 68.34 ms | 96.11 ms | ― |
| 列ごとの支持行区間を導出して走査する `interval` | 未計測 | 未計測 | 最良でも23.62 ms |

`atom_major` はatomic加算を大きく減らしたが、dWとサイト幾何の読み直し、長いループが勝った。`fused` は同じ窓を再利用しても、融合カーネルの負荷が大きかった。`staged` のサイトタイルとatomレーンを小幅に変えても約9.6 msで横ばいで、タイル積を増やすとレジスタ資源の崖に当たり、100 ms以上になる構成があった。`interval` は小形状の独立参照勾配3件に一致したが、三角関数、細かいループ、dWの再読込が重く、現行より遅い。後者の区間端はFP32誤差を見込んで4行広げる実験実装であり、全パラメータ範囲に対する保守性は証明していない。遅い経路は既定にしない。

## 候補atom一覧によるbackward

`staged_listed` は、各stationの16×64サイトタイルと交差する可能性があるatomだけを、backwardの最初に一覧へ詰める。4次元サイト位置のaxis-aligned bounding boxとatomの球状支持域の下界を使い、境界ではFP32誤差に備えて `precision × 下界 ≤ 1.0001` を残す。atomが支持域内のサイトを持つ場合に除外されない保守的な条件である。4096²の初期配置では16×32タイルの候補を28.4%、16×64では28.2%除外できた。16×64にすると一覧を作る時間は1.51→0.83 ms、一覧容量は6.72→3.36 MBになる。8192²では5.91→3.15 ms、26.87→13.43 MB。初期配置での最大候補数は両サイズともstation当たり205個なので、一覧は32 bitの絶対atom番号ではなく8 bitのstation内番号で保持し、カーネル内でbucket offsetから絶対番号へ復元する。候補数が256を超える配置では16 bit、65536を超える配置では32 bitへ切り替える。

atom勾配は既存の最大1024行の局所dW窓を読み、1 warpが1 atomずつサイトの勾配を縮約する。16×64タイルで局所atom勾配は1024行窓当たり4096²で3.47 ms、8192²で6.75 msだった。従来の8 atomレーン・4 warp構成では6.15/12.18 ms。atom数を多くまとめると、このタイルサイズではレジスタ使用とスピルが急増した。小さい8×64タイルは局所kernelだけなら3.22/6.36 msだが、一覧生成が1.51/5.90 msへ増えるため、学習全体では16×64を選んだ。全重みW・全dWは一度も保持せず、局所dW窓を行ごとに上書きする。

候補一覧の32 bit絶対番号版は4096²・M=128で50.71 ms、ピーク199.35 MB。8 bit局所番号にすると50.21 ms、ピーク178.39 MB。さらに1 warp化で39.85 ms、16×64化で39.22 ms、ピーク174.96 MBとなった。8192²・M=128は同じ順に190.92→189.77→152.19→148.09 ms、ピーク683.22→603.00→603.00→589.32 MB。大きいバッチでも表のとおり改善し、denseよりピークは低い。`staged_listed` は[試作の選択肢](../prototypes/block_streamed_backward.py)と[測定CLI](../prototypes/benchmark_mapped_training_memory.py)の `--atom-kernel staged_listed` で選ぶ。既定のbackendはまだ変更していない。

他の検証では、既存atom群をboxで条件分岐するだけでは1024行窓が8.63→8.81 msと遅くなった。atomicを避けるpartial勾配方式も4096²・M=128で59.45 ms、ピーク205.13 MBとなり、`staged FMA` より悪い。Triweightの多項式モーメントを列方向に前計算する方式は、64 stationだけの比較でも局所atom勾配が0.61→1.51 msで、追加scratch約20 MBを要し、数値差も残った。候補一覧のタイル形状とwarp数を個別計測した結果は `output/triton-a100-20260928/` に保存した。

## 支持域の実測と次の設計条件

従来の「32列小片を除外できる割合は約0.3%」という値だけでは、atom×siteの無駄な評価数は分からない。初期配置から各32 stationを標本抽出して全サイトを直接判定すると、4096²でatom×siteの**44.88%**、8192²で**44.93%**が支持域内だった。4096²の16×32タイルではatom×タイルの30.9%が完全に域外、8×8なら40.8%、4×4なら48.2%だった。各列で有効行は標本上連続しており、理論上は行区間への走査で距離評価を減らせる。ただし今回の単純なatom主体の実装はデータ再利用を失い、速度は悪化した。この標本値は学習後の分布やあらゆる形状の保証ではない。

現時点で**backwardが速度ボトルネックだと断定できない水準には達していない**。`listed 1 warp` の4096²・M=128ではforward約15.9 msに対してbackward約28.2 ms、8192²・M=2048ではforward約80.3 msに対してbackward約155.3 msだった。学習ステップのCST/dense速度比はM=128で約10倍、M=2048で約2.2倍。これはCSTの原理的な限界を示す結果ではなく、この実装と初期atom配置での測定値である。次は単一warpの長いatomループをさらに短くできる構成を探す。速度改善は追加メモリと数値精度を合わせて判定する。

GPU eventでbackwardの各段を分けると、4096²・M=128は重み窓生成9.0 ms、入力勾配GEMM0.7 ms、一覧生成0.8 ms、局所dW GEMM0.7 ms、atom縮約13.5 msだった。8192²・M=128は順に35.9、2.6、3.1、2.5、52.4 ms。M=2048では4096²の二つのGEMMが各約9.5 ms、8192²では各約38 msに増え、重み窓生成とatom縮約はほぼ一定だった。GPU eventの合計はPython側の同期や準備時間を含む学習ステップ時間とは一致しない。重み生成のwarp数を1/2/4/8、タイル形状を数種類比較したが、現行64×32・4 warpの1024行窓当たり2.31/4.53 ms（4096²/8192²）から有意に改善しなかった。1 warpではregister spillが起き、2.63/5.04 msに悪化した。atomループのソフトウェアパイプライン化も、基準3.46/6.74 msに対して2段で3.84/7.46 ms、2回展開で3.93/7.68 msと遅くなった。したがって次に狙うべき中心はatom縮約の計算構造そのものである。
