# 128 atomのグループとHの生成・最終利用の担当案

2026-10-23。[128で検証済みの初期データ](hierarchical-fourier-128-execution-20261023.ja.md)から
具体的な並び替え・producer/consumer表を作成した。以下のG番号・block名・Hscratchは
**次の実装の設計案**であり、新しいgrouped CUDAの実行結果ではない。
保存済みGPU geometryの読取、全128 atomの一意な分類、CPU上の並べ替えた数値和を検査した。
新しいGPU jobは投入していない。

## 分類と並べ方

active componentのprofile階層幅の組、現行route、共有Fourier bankの組で19分類する。
各分類内を入力支持始点→出力支持始点→atom IDの順に並べ、最大4 atomで区切る。
その結果39グループ：局所10 group/31 atom、直接縮約21 group/74 atom、
階層Z利用8 group/23 atom。元のPは動かさずindexで参照し、Parameter IDやoptimizer状態を保つ。
入力を近づける並びだが、同一groupの全入力が1 tileに収まることは保証しない。
Xの共有範囲は各atomの実支持とその和集合で別途決める。

ここで階層幅はMetaのtile幅をspacing=.1でsite換算したもの。
σ・支持全幅・kernel実行tile幅32とは別の値である。
2段にまたがるblendを1段へ丸めず、例えば `2+4`、`64+128` をそのまま分類keyにする。
`128+256`の256はdomain外まで広がるprofile componentで、Z256を確保する意味ではない。
128 domainに対応する共有bankがないcomponentは既存の直接/残差経路を保つ。
局所判定は既存prototypeの31 atomに合わせ、74 atomへの追加融合は今回の案に混ぜない。
これはH保存方法や4 atom単位の最適性を測って決めた結果ではない。

Hを作る順序と、出力を集約する順序は二つのindex表に分ける。

- producer表：上記の39 group。係数やPはatomごとに独立のまま。
- 局所出力表：32-site出力tileごとに、支持が重なる局所atom/groupを参照。
- C表：bank/nodeごとに `(atom,component)` を参照。同じHを複数成分が使っても重みは保つ。
- 残差表：出力tileごとに、非局所atomの直接成分/境界残差を参照。

入力・出力tileの所属を両方とも厳密なkeyにすると、この初期状態では92分類になり、
74分類が1 atomだけだった。今回はproducerの入力順とconsumerの出力indexを分ける案にする。
振幅0のatom0や空支持のatom3もParameterから削除せず、全128個を表に残す。
幅・中心が更新されたstepでは支持・分類・indexを再構築する。

## blockの担当

図のb0はbatch0..3、b1は4..7、…、b7は28..31。SM番号ではない。

| 担当名 | 読むもの | 作る/保存するもの | Hの最後の利用 |
| --- | --- | --- | --- |
| L(t,b) | 出力tile tの局所リスト、X、Norm、Native値 | block内h/acc、最後にglobal Yへstore | 同じL block内のacc加算 |
| P(g,b) | group gのXまたはZ＋直接残差、係数 | global Hscratchへ未スケールΣXvをstore | このblockでは消費完了しない |
| C(n,b) | wave内H、node nのcomponentリスト、Beta/Norm/P | global Cへ部分係数を集約 | 残差を持たないatomではここが最後 |
| R(g,b) | group gのH、出力残差、Norm/P | global Yへ残差を加算 | 残差を持つatomではここが最後 |
| F(t,b) | global CとY、固定basis | 同じYにCの展開結果を加算 | Hを読まない |

Lは既存の8-worker方式を想定する。job=`t+4*b`、worker=`job%8`。
各workerは複数jobを担当し、各jobは出力tileの全局所groupを集約する。
groupごとに別Lを立てて同じYへ上書きする構成にはしない。
局所hは実装時の論理的なon-chip値。register/sharedへの個別配置は未検証。

非局所は1 wave最大16 atomとする仮の説明用上限を置き、group境界でpackする。
Pはwave内group×8 batch群を並列に生成する。Cはnodeの出力ownerで、
同じwaveに複数groupの寄与があっても、そのC要素を一つの担当が集約する。
Rはgroup×batch群で出力の直接成分/境界残差を処理し、group間で重なるYには加算を使う。
初案ではP完了→C pass完了→R pass完了のkernel境界で順序を付ける。
RのY書込み前には局所Yの初期store完了も必要。Cの集約は局所Yを読まない。

Hの値だけならscratchの仮容量は `[B32,16]` FP32 = 2,048 bytes。
現行の `[32,128,3]` を確保し続ける実装から変更が必要で、未実装である。
Z/Cや準備cache、optimizer等の容量は別で、GPU総ピークが2,048 bytesになる意味ではない。
準備cacheもwave単位にする変更と、その勾配・性能検証は別に必要。
並列stream間で同じ準備領域を上書きするなら、全利用者の完了待ちも必要になる。

## 局所の実例：G02 = [89,93,12,46]

profile階層幅2+4、入力/出力は各atom独立。batch0..3での担当は次の通り。

```text
                  G02のprofile/Norm、X
                    /       |       \
L(t1,b0), worker1     L(t2,b0), worker2     L(t3,b0), worker3
  atom89                atom12,46             atom93,12
  h→acc（block内）      h→acc（block内）       h→acc（block内）
  Y[:,32..63]へstore    Y[:,64..95]へstore     Y[:,96..127]へstore
```

他の局所groupも同じL担当に集約する。atom12は入力92..99、出力93..100。
L2は入力を縮約して出力93..95へ、L3も入力を縮約して出力96..100へ使う。
この初案ではその二重計算を残し、Hのglobal受け渡しをしない。
最後のH利用者は各L自身のacc更新で、accは担当Yのstoreまで保持する。

## 階層の実例：G38 = [31,105]

両atomはprofile階層幅128+256、共有bank9、入出力支持0..127。
共有componentに加え、同じatomの直接成分も保持する。
入力Hに必要な共有nodeは25、依存closureは `[4,5,6,7,18,19,25]`。
node4..7が32 sites、18/19が64 sites、25が128 sitesを表す。
親の偶数周波数は子から継承できるが、残る周波数は各段でXを読んで計算する。

```text
Z32 nodes4..7 → Z64 nodes18,19 → Z128 node25
       ＋ 各段のX読込                ＋ Xの直接成分
                                           ↓
                                 P(G38,b0) がHを生成
                                           ↓
                           global Hscratch[0..3,2..3]
                             8 scalars、FP32、32 bytes
                                           ↓
                           C(node25,b0) が係数C25へ集約
                                           ↓
                           R(G38,b0) がYへ直接成分を加算
                                ↑ 局所Y完成も待つ
                                           ↓
                            wave6のR pass完了：Hは不要
                                           ↓
                         全wave後、F(t,b0)がC→Yを展開
                                 FはHを読まない
```

wave6では先にG37の2 atomがslot0/1、G38がslot2/3を使う。
Pのgridを `(wave内group数,8)` とすれば、G38/b0のproducerはblockIdx=(1,0)。
この番号は提案kernelの論理配置であり、既存GPU traceのblock IDではない。
R(G38,b0)は2 atomとも残差を持つため、このbatch群のHの最終利用者になる。
全batch群のR kernel完了後、wave全体のH領域を再利用できる。

一般にはCだけを使うatomのHはC passが最後、残差のあるatomではR passが最後。
完了順の異なるCTAのどれが最後になるかを仮定せず、passの完了境界で再利用を制御する。
最終YのFまでHを保存し続ける必要はない。backwardは現行と同じ再計算方針を仮定する。

## 寿命を分ける

| 値 | 最後まで必要な利用者 | 再利用できる境界 |
| --- | --- | --- |
| 局所h | 同じL内のacc更新 | その値の最後のacc加算後 |
| 局所acc | LのY store | 担当jobのY store後 |
| waveのglobal H | C、必要ならR | waveのC/R pass完了後 |
| waveの係数/Norm/Native | P、C、R | waveの全利用者完了後 |
| global C | 最終F | 全waveの集約後、Fの展開完了まで |
| global Y | 呼出し側・loss | operatorの出力として返す |

## 検査と原本

保存GPU値のSHA256を回収済みhash manifestと再照合した。
128 atomの所属が重複・欠落なし、局所出力リストが既存の39所属と完全一致、
Zの依存closureとC nodeが保存済みdemandの範囲内にあることをassertした。
グループ順の独立FP64和と元の独立和の最大差6.67e-16、保存GPU Yとの差2.21e-7。
これは並べ替え・参照のCPU検査であり、新しいCUDA実装や速度の検証ではない。
原本jobは `l4job-6153458561a94e118b12c9d0985dfa2f`。
