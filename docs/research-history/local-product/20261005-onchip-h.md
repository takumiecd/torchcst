At N128 the recomputed VJP improves the no-G control by 4.5% with the same allocated
peak. It is about 0.3% slower than the saved-G speed control, effectively similar
latency, while using 18.1% less allocated memory. It approaches dense at about
3.49x dense time; it does not improve the absolute speed winner. At N64 the
unroll/recomputed-VJP combination improves the existing control about 1.5%, at
the same allocated peak, and takes about 1.98x dense time. The improvement is
small and is reproduced in both paired executions; no statistical significance
claim is made. All CST candidates reserve 6MiB; dense reserves 46MiB. These are
allocator observations, not GPU process usage.

Retain 16-site owners. Prefer the recomputed-VJP candidate for the N128
control-peak objective and its unroll variant for ordinary N64. Do not enable
the unroll at N128: it erases most of the VJP benefit. Cache/DRAM residency
remains unproven. Forward/dX general-band traversal remains the larger latency
target; eliminating unnecessary backward retention of forward-only H is a
separate future memory experiment.

## Initial tile-width results

The first cohort is negative for speed. At N128, saved-G/no-G controls take
159.672/167.966us; cached 32/64-site tiles take 200.523/221.601us and recompute
32/64-site tiles take 202.154/224.257us. Dense takes 45.781us. At ordinary N64,
the existing bounded-unroll control takes 79.204us, cached tiles96.529/104.074us,
and recompute tiles93.978/103.716us; dense takes 38.918us.

Recomputation lowers N128 allocated peak419,328→314,368 bytes against the no-G
control, and N64 peak154,112→128,000 bytes. CST candidates all reserve 6MiB.
The recompute32 N128 forward reports 2 spill slots, so its entire temporary state
cannot be described as resident on chip. Wider owners reduce N128's grid from
16 CTAs to 8/4 and increase register/shared requirements. Separate instrumented
forward/dX times rise; reduced parallelism is a plausible contributor, not a
hardware-counter-proven causal claim. These wide tiles are not selected for speed.

The parameter VJP is different: full recomputation simplifies the mixed
saved/local branch. Its N128 diagnostic median drops 24.58→16.38us and reported
spills 110→0 against the no-G control. A follow-up keeps the original 16-site
forward/dX owners and cached wide-H producer but recomputes parameter H.
The `_unroll` variant also enables the existing bounded middle-support unroll.
This isolates the useful backward change from the slower wide ownership.

## Implementation and contract

Output owners span 32 or 64 sites instead of 16. They consume their constituent
singleton buckets, scan each general band once, and reuse the batch-by-atom H
contraction across the wider output tile. There are no partial output buffers or
output atomics. Cached controls retain the existing wide-H producer and its
fixed B*A allocation. Recompute routes omit that buffer and producer, compute H
within output owners, and recompute it for the parameter VJP.

The Triton compiler chooses register/shared placement; the implementation does
not guarantee L2 residency or eliminate physical DRAM traffic. Shared memory is
local to a CTA/kernel. A buffer allocation is not a DRAM traffic measurement.
Compiler register/spill/shared reports and optional hardware counters are
separate evidence from PyTorch allocated/reserved peaks.

The mathematical contract is unchanged: production PolarAmpWidth, full-domain
normalized Triweight product, live widths and support, exact singleton and empty
support handling, dX and all atom gradients. The 128 mixed case includes
sigma/spacing 0.25 and 0.75 with sigma_min/spacing=0.25; the 64 case starts at
ordinary sigma/spacing=3. All widths continue updating during training.

## Measurements and evidence

Measurements use the existing Linear runner, batch32 FP32, TF32 disabled, fused
AdamW plus production fused Polar update. The main time is the uninstrumented
complete-step CUDA Graph median with 21 samples per execution. Instrumented
phase/kernel events use a separate Graph; they are not added or subtracted from
the main time. Allocated and reserved peaks include capture/replay; process-wide
GPU memory is unmeasured. Dense uses the same input and optimizer settings with
its own dense parameters; every CST candidate starts from matched parameters.

The initial Nsight probe profiles one warmed output kernel with
`--cache-control none`, excluding the H producer, metadata, backward and
optimizer. It reports 0 DRAM read bytes for all three probed plans, but warns about
uncontrolled caches and reports impossible L2 hit ratios 128.79/206.29/191.99%.
These raw values are preserved and excluded from cache-residency claims. They
are not a complete-step DRAM measurement; no reliable L2 hit improvement is
established.

Results are recorded in [the machine summary](20261005-onchip-h.json).
Raw outputs/drivers stay in the worktree's ignored
`benchmarks/cuda/linear/evidence/onchip-h-20261005/` and the shared pool's
`~/.local/state/colab-l4-pool/jobs/JOB_ID/`; each pool job preserves its frozen
`source.tar.gz`, driver, transport log, result archive and receipt. Reproduce a
job by extracting its snapshot and running its `__pool_driver__.py` with the
arguments in `spec.json` and a fresh `CST_JOB_OUTPUT` directory.

The benchmark command for each case is:

```bash
python -m benchmarks.cuda.linear.run \
```
