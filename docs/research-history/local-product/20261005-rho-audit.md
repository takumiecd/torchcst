# Matched 64/128 audit with initial rho strictly above one

Measured source: `e5e6cc764e348b8a4b98494dfffb1e2f94250125` on `kernel/local-product-onchip-h`.
The user requires every initial sigma/spacing to exceed1. Cases initialize at
rho1.25,1.5,2,3,4,8,16. Minimum/birth/maximum remain0.25/0.25/16;
production PolarAmpWidth and the fused polar update continue changing widths.
No fixed sigma is injected. Earlier proposed subspacing Cases were withdrawn
before GPU submission; their CPU preflight remains ignored evidence only.

## Outcome

**The largest measured width is not the slowest case.** Both shapes are slower
near initial rho3/4 than at rho8/16. The primary next target is the local
forward/dX schedule at N128, especially around rho2–4. This experiment identifies
where latency accumulates; it does not prove DRAM bandwidth, input-load
instructions, metadata traversal or support-loop arithmetic is the root cause.

The rho4 label is particularly important: every atom crosses from the initial
wide band to the middle band during training; final rho is about3.93. Rho8/16
remain in the saved-wide band. This is an initialization sweep of evolving
training trajectories, not a frozen-rho sweep or a causal cutoff intervention.

## Matched protocol

- NVIDIA L4 /58 SMs, Torch2.11.0+cu130, CUDA13.0, Triton3.6.0.
- N64/B32/A204 and N128/B32/A819 (~5% of dense weight elements), FP32/IEEE, TF32 off.
- Atom block32, batch block16, output owner16 and contraction warps4 for both sizes.
- Matched centers, nominal amplitudes, input and target within each size;
  only initial activity radius/width changes. Centers use grid jitter0.1.
- Fused capturable AdamW proposals plus production fused Polar update; seed41,
  warmup5 and21 timing samples per independent execution.
- Four sequential pool jobs on the same L4 VM, two independent executions per
  condition. Fresh runner processes/models/optimizers/inputs; repeat2 reverses
  both rho order and candidate order. Two executions are not confidence intervals.
- Both routes retain cached wide forward H. The control also saves backward G;
  the candidate recomputes parameter H and does not save G. These are executable
  schedules, not a change to a single storage instruction.
- This controls recipe settings across sizes. It does not replace the existing
  N64 atom16 bounded-unroll tuning objective or search all available launches.

faster at most widths; tiny differences are not statistical significance claims.

## Reproduction

Use `benchmarks/cuda/linear/plans-local-onchip.json` and
`cases/local-rho-audit-{64,128}-rho{1_25,1_5,2,3,4,8,16}.json`.

```bash
python -m benchmarks.cuda.linear.run \
  --plans benchmarks/cuda/linear/plans-local-onchip.json \
  --case benchmarks/cuda/linear/cases/local-rho-audit-128-rho3.json \
  --polar-update fused --phase-diagnostics --kernel-diagnostics \
  --source-commit e5e6cc764e348b8a4b98494dfffb1e2f94250125 \
  --output output/rho-audit-128-rho3.json
```

For the exact job, extract its frozen source and execute `__pool_driver__.py`
with the source commit, size and repeat arguments from `spec.json`, setting
`CST_JOB_OUTPUT` to a fresh output directory.
