# Matched sigma/spacing: local H versus saved H

Research branch `codex/local-product-hybrid`, parent `f22068d`.
The user asked to test the width/reuse hypothesis before further mixed-route
optimization: narrow atoms should benefit from local H, broad atoms from saving H.

## Experiment design

The earlier homogeneous-profile table did not isolate this hypothesis. Its
`polar` route computed H over the full padded input axis even for narrow sigma.
The support hybrid adds classification, a producer launch and fixed-capacity H
scratch even when every atom is narrow. It is not the pure narrow local route.

This experiment adds two research routes to the **existing Linear runner**:

- `polar_support`: fused current-state polar preparation plus unconditional
  positive-support contractions for local H, transposed dX, and parameter VJP.
  No H tensor is stored between kernels.
- `polar_support_saved`: the same preparation and support arithmetic, with a
  separate support-bounded H producer. H[B,A] is reused in forward and parameter
  VJP; dH, G and dG still use the current support contractions. No mixed-route
  classifier or packing is involved.

Both use canonical atom order, atom block16 and batch block16. Both prepare13*A
metadata on every forward, normalize over the full domain before local slicing,
and preserve singleton/floor/empty support, all gradients, and the production
PolarAmpWidth activity update. The old group support fallback and mixed hybrid
routes remain available. H->Y remains a full padded dot. This is a small
transformation primitive; no W materialization or outer GEMM is introduced.

This is a comparison of two executable schedules, not an intervention changing
only a DRAM store instruction. The saved producer exposes batch/atom CTAs;
fused local forward uses batch CTAs looping over all atoms. Register/shared
usage and parallelism may therefore influence the result independently of rho.
The saved route also still reads X for center derivatives in backward, so
saving H need not eliminate those input reads. Wider support alone cannot prove
that saved H will win, or define a universal cutoff.

Cases have N64/B32/A205 and N128/B32/A819 (~5% of dense elements), spacing1,
FP32/IEEE, initial rho in [1,1.5,2,3,4,8,16], seed41, warmup5, rounds21.
`rho*` labels specify **initialization only**. All candidates perform real
forward/backward/fused capturable AdamW proposals plus polar activity updates;
no sigma freezing is used. Every forward rebuilds sigma/support from live state.
Initial centers and normalized amplitudes match across all rho values. Rho1
uses fractional centers and generally spans two sites; it is distinct from the
aligned `sharp` one-hot fixture. Sigma_min=spacing=1 for these fixtures, not a
new universal mathematical constraint.

Each candidate runs in a fresh process; all candidate initial parameter/input
hashes must match within its case. Matrix-based local/saved controls are also
measured at initial rho3 and16. Ordinary dense complete-step references are
measured at rho3 for each shape with the same input, batch, FP32 settings and
AdamW contract. Primary CUDA Graph step time remains uninstrumented; allocated
and reserved peaks include capture/replay and are saved before diagnostics.
Total GPU process peak is not measured.

The optional `--phase-diagnostics` captures a **separate** graph with external
CUDA event nodes after the primary timing/memory measurement. Training and sigma
updates continue. Forward+loss, backward, and optimizer times include event
instrumentation overhead and are explanatory diagnostics, not replacement
complete-step timings or memory peaks. The reported final sigma vector is the
state at the end of the primary measurement, before this additional graph.

### Phases and limits of attribution

The separate event-instrumented training graph gives these N128 phase medians:

| Initial rho / H policy | Forward+loss ms | Backward ms | Optimizer ms |
| --- | ---: | ---: | ---: |
| 1 / local | 0.119808 | 0.113664 | 0.091136 |
| 1 / saved | 0.091136 | 0.114688 | 0.091136 |
| 3 / local | 0.132096 | 0.126976 | 0.091136 |
| 3 / saved | 0.092160 | 0.128000 | 0.091136 |
| 16 / local | 0.216064 | 0.220160 | 0.091136 |
| 16 / saved | 0.095232 | 0.221184 | 0.091136 |

The width-dependent advantage appears mainly in forward. The saved schedule
exposes H production over atom blocks; fused local forward runs two batch CTAs
and loops over atom blocks. These results support investigating broad-H reuse,
but do not attribute the entire gain to eliminating backward recomputation or
to particular cache hit rates. Backward still reads X for center derivatives;
saved H is an extra read there and measured backward time is almost unchanged.
No hardware cache counters or L1/L2 residency were measured. Both new routes
report zero spill slots for all kernels; this does not imply every byte remains
on chip.

At N64 the optimizer alone takes about0.087–0.088ms in the instrumented graph;
at N128 it takes about0.091ms. Other phases and the optimizer therefore influence
complete-step width cutoffs. No universal cutoff follows from rho alone.

### Arithmetic path controls

Matrix-based H contracts over the entire padded axis. It is advantageous for
broad support compared with a serial direct-support loop, even in saved mode:

| N / initial rho | Support local ms | Support saved ms | Matrix local ms | Matrix saved ms |
| --- | ---: | ---: | ---: | ---: |
| 64 / 3 | 0.155542 | 0.148610 | 0.143792 | 0.140287 |
| 64 / 16 | 0.214772 | 0.186653 | 0.143714 | 0.140442 |
| 128 / 3 | 0.352247 | 0.312959 | 0.375058 | 0.323770 |
| 128 / 16 | 0.531162 | 0.409665 | 0.378000 | 0.324096 |

At N128/rho3, saved support H is3.3% faster than matrix saved H. At rho16,
matrix saved H is20.9% faster than support saved H. Thus **H lifetime and the
method for contracting its support are separate tuning decisions**. A broad
saved path should not be forced to retain the serial support algorithm used by
narrow atoms. N64 matrix saved controls are faster than both support routes at
the measured rho3/16 controls. Ordinary dense complete steps are0.039252ms
(N64) and0.045873ms (N128); dense remains faster than these CST candidates.

## Decision

Retain both routes as verified research alternatives; do not install a hardcoded
local/saved crossover. The larger-rho saved-H benefit is supported in these
shapes. The narrow-local speed claim remains unproven: this local forward still
loops over all atoms within two batch CTAs and uses a padded output dot, while
the saved producer has additional atom parallelism. The memory benefit of local
H is already measured.

The next hybrid design should consider actual support and reuse, execution
parallelism and arithmetic path together. A useful targeted follow-up is to
make narrow local output ownership/atom groups efficient before repeating this
same matched sweep. Actual use across multiple output tiles is a later GEMM
composition question. Keep sigma dynamic, retain the mathematical contract and
continue using the same benchmark runner.
