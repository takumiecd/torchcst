# Compact support外の演算量と列区間の省略

> この文書の `prototypes` 実行例は commit `190a1bb3fa6259fde493a30d901d5cab7c2ebb82` 時点の
> 歴史的な再現手順です。削除したコードの参照方法は
> [旧実験コード](../legacy-prototypes.ja.md)を参照してください。

2026-09-26。[複数出力特徴で入力を共有する直接計算](block-output-sharing.ja.md)の続き。

後続の[目標atom密度での再測定](target-atom-density.ja.md)では、atom数をdense要素数の5%に設定した。
以下の低密度の結果を、その目標密度での性能として扱わない。

## 結論

今回の区間省略は標準には採用せず、現行の64列atom dotを維持する。
4096²/M128/8192 atomsではdotに含まれる要素の37.58%がゼロだったが、
16×16の領域を丸ごと省けるのは4.24%、事前のbox判定で省けるのは0.53%だった。
ゼロは各領域内に散らばっており、ゼロ要素の割合をそのままdot削減率にはできない。
細分化・判定の費用があるため、実測でも大きな速度改善にはつながらなかった。

この結果はcompact support自体が無効という意味ではなく、現在のchart・初期atom分布と
16出力行単位のdotに対し、16/32列単位の省略余地が小さいことを示す。
学習後や別のsupport幅に同じ割合を保証しない。

## 問い

現行のatom dotは、行単位の粗い判定を通ると16出力特徴×64列の寄与を評価する。
profileがゼロの場所も、その後のdotの形には含まれる。
ここで測るのは次の2つであり、同じ値ではない。

- 寄与がゼロになる要素の割合。
- 16×16または16×32の領域が丸ごとゼロで、dot全体を省ける割合。

## 実装

- `block_support_diagnostics.py`：CST各station・16出力行・候補atomごとに
  現行64列dotの呼び出し数、非ゼロ寄与数、小区間が丸ごとゼロの数を数える。
  さらに保守的なbox判定の通過数と、その判定が見逃した非ゼロ数を数える。
  診断は速度計測の外で実行する。
- `section_bounds`：列区間のsection座標を囲むboxを求める。atom更新には依存しないが、
  今回はキャッシュを追加せず、各forwardのprepared geometryから作り直す。
  この準備コストも測定に含める。
- `column_tile`：CST tileを変えず、実行上の列幅BKを16/32/64で比較する。
- `support_cull="bounds"`：区間boxに届かない候補を評価・dotの前に省く。
- `support_cull="exact"`：box判定に加え、評価した寄与がすべてゼロならdotも省く。
  正確なゼロ検査はprofileを評価した後なので、その評価コスト自体は省けない。
- 省略版は、最初に必要なatomが見つかるまで入力のロードを遅らせ、以後は再利用する。

従来の`column_tile=None, support_cull="none"`は維持する。
全Wを展開せず、出力の書き手も一つ。GPU forwardのみのprototype。
細分化で浮動小数点の加算順序は変わるため、既存と同じatol=rtol=3e-5で検証する。
box判定の余裕は候補を増やす方向であり、出力のprofile値は変更しない。

## 条件

A100 80GB PCIe、MIG3g.40gb・42 SM。Torch2.6.0+cu126/Triton3.2.0。
FP32、TF32無効。Strip + Torus、raw Triweight、CST tile64×64、seed21。
同じケース内でatom表・chart・入力・比較用dense Wは共通。
CUDA Graphで準備込み、各経路3ラウンド、rep20ms、順序を交互に反転、中央値。
通常Python実行の壁時計時間とdense W生成は含めない。

診断は論理的なprofile要素とdot領域の数であり、実際の命令数・HBM転送量・cache hit率ではない。
M方向の64行グループ間で同じ寄与を再計算するため、診断では1グループあたりの数を示す。

## 検証

- 診断の非ゼロ数を、小さい端数形状のcanonicalな全atom寄与と一致させる。
- 16/32列のbounds/exactそれぞれで、CST高さ5・幅192、物理17×197、入力65行・振幅0を検証。
- 同じ4構成でI/B境界・Torus継ぎ目・CUDA Graph後の振幅/位置更新を検証する。
- 既存の標準経路とTorch参照も維持する。
- 大型ケースはcanonicalな全atom和で1,024ランダム点＋128行の最大絶対値要素を点検し、
  全出力を同じWのdenseと比較する。独立に全Wの全要素を評価する検証ではない。
- box判定による非ゼロ寄与の見逃しは0を要求する。

## ゼロの分布

M方向の1グループあたりを診断する。Mだけを変えたケースは同じ幾何のため同じ数になる。
exactは実際に非ゼロ寄与が一つもない領域、boxは評価前の保守的な判定。

| N / atoms | ゼロ要素 | boxで省略16列 | 全ゼロ16列 | boxで省略32列 | 全ゼロ32列 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 4096 / 8,192 | 37.580% | 0.526% | 4.237% | 0.242% | 4.157% |
| 8192 / 16,384 | 37.057% | 0.869% | 3.334% | 0.480% | 3.119% |
| 4096 / 131,072 | 37.403% | 0.720% | 4.095% | 0.357% | 3.926% |

全ケースでbox判定による非ゼロ寄与の見逃しは0。
正確な全ゼロ検査はprofile評価後なので、dotを省けてもそのprofile評価は実行済み。

### 現行dotの論理的な積和量

1回のdotの16×64要素に入力行数Mを掛ける。今回Mは64の倍数なのでbatch paddingはない。
これはdot部分だけの積和（MAC）数で、距離・profile・候補判定・ロード・同期を含まない。
実命令数やGPU利用率の測定ではない。

| N / M / atoms | atom dot MAC数 | dense MAC数 | 比率 |
| --- | ---: | ---: | ---: |
| 4096 / 128 / 8,192 | 3,085,434,880 | 2,147,483,648 | 1.437× |
| 4096 / 512 / 8,192 | 12,341,739,520 | 8,589,934,592 | 1.437× |
| 8192 / 128 / 16,384 | 6,129,582,080 | 8,589,934,592 | 0.714× |
| 4096 / 128 / 131,072 | 49,349,394,432 | 2,147,483,648 | 22.980× |

8192²ではdot部分の論理的なMAC数がdenseの約0.714倍だった。
それでも全forwardはdenseより遅い。距離/profile評価、ループ・判定・データ供給や
縮約の実行効率を調べる必要がある。MAC数だけで演算律速/帯域律速やTritonの限界は判断できない。
一方、131,072 atomsではdotだけでdenseの約22.98倍のMACがあり、
atom密度の増加を同じ直接計算で扱う費用は大きい。

## メモリ・検証結果

追加割当ピークは出力込みで、保持済みの入力・モデル・prepared・比較用Wを除く。
省略用のboxの作成により、16列boxは現行より1,536 bytes、32列boxは512 bytes増える
（4096²/M128/8192 atoms）。全W相当の一時配列は作らない。

- A100 **47 tests passed**（60.20秒）。ローカル4 passed / 43 skipped（CUDAなし）。
- pilot10経路と大型3条件×7経路、計31経路で出力全体をdenseと比較し合格。
- 各ケースのcanonical点検、診断の見逃し0、bucket総数、全atomがIに所属、3ラウンド、
  完了フラグ、source commit、A100/42 SMを確認した。
- データ依存の省略を含むCUDA Graphをcaptureし、atom更新後の出力も検証した。
- 誤差許容値はatol=rtol=3e-5のまま。今回の範囲で非ゼロを落とす近似は導入していない。

## 次に優先すること

今回の粒度での区間省略をさらに作り込む優先度は下げる。
次の対象は、M方向のグループで同じatom寄与を繰り返し評価する処理の共有と、
入力供給・縮約の実行効率。ゼロが少ない矩形だけへ詰め直すなら別途配置や制御の費用がかかる。
現在のメモリ優位を保ちながら、それらを含む全forward時間で比較する必要がある。
